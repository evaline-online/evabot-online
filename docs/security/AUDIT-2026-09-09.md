### Уязвимость: SSH открыт во всё интернет

| Параметр | Было | Стало |
|----------|------|-------|
| **Firewall `allow-iap-ssh`** | `sourceRanges: пусто` → `0.0.0.0/0` (весь интернет) | `sourceRanges: 35.235.240.0/20` (IAP только) |
| **OS Login** | **Не включён** — легаси SSH-ключи в project metadata | `enable-oslogin=TRUE` |
| **SSH-ключи в метаданных** | `ssh-keys: evabot:ssh-rsa AAAA...` (прямой доступ из интернета) | Удалены (заменены IAM) |
| **IAM для SSH** | Пустая политика — только project-level key | `roles/compute.osAdminLogin` для 2 участников |
| **Теги на VM** | Нет (firewall применялся ко всем) | `allow-iap-ssh` на обеих VMs |

### Риски до ремедиации

1. **Критический:** порт 22 доступен с любого IP в мире. Любой может пытаться подобрать пароль или использовать уязвимости в SSH-ключах.
2. **Высокий:** легаси SSH-ключи в project metadata не имеют отзыва по отдельным пользователям — один скомпрометированный ключ = доступ ко всему.
3. **Средний:** отсутствие аудита — нельзя понять кто именно подключается (ключ привязан к проекту, а не к человеку).

## ✅ ЧТО СДЕЛАНО

### Шаг 1: Включён OS Login (управление доступом через IAM)

```bash
gcloud compute project-info add-metadata \
  --metadata="enable-oslogin=TRUE"
```

OS Login заменяет project-level SSH-ключи. Теперь доступ управляется через IAM-роли:
- `roles/compute.osLogin` — обычный пользователь (без root)
- `roles/compute.osAdminLogin` — администратор (root через sudo)

### Шаг 2: Пересоздан firewall rule с IAP-only access

```bash
# Удаляем старое правило (открыто для 0.0.0.0/0)
gcloud compute firewall-rules delete allow-iap-ssh --quiet

# Создаём новое — только из IP-диапазона Google IAP
gcloud compute firewall-rules create allow-iap-ssh \
  --network=default \
  --direction=INGRESS \
  --priority=1000 \
  --source-ranges=35.235.240.0/20 \
  --target-tags=allow-iap-ssh \
  --allow=tcp:22
```

Порт 22 теперь **доступен ТОЛЬКО** из Google IAP IP-диапазона (`35.235.240.0/20`). Прямой доступ из интернета заблокирован.

### Шаг 3: Добавлены теги на обе VMs

```bash
gcloud compute instances add-tags evabot-agent-vm \
  --tags=allow-iap-ssh --zone=europe-west3-a

gcloud compute instances add-tags evaline-micro-vm \
  --tags=allow-iap-ssh --zone=us-central1-a
```

### Шаг 4: Удалены легаси SSH-ключи

```bash
gcloud compute project-info add-metadata \
  --metadata="ssh-keys="
```

### Шаг 5: Назначены IAM-роли

| Пользователь | Роль | Доступ |
|---|---|---|
| `evabot.online@gmail.com` | `roles/compute.osAdminLogin` | Root через sudo (админ) |
| `olegzai.server@gmail.com` | `roles/compute.osAdminLogin` | Root через sudo (админ) |

### Проверка подключения

```bash
gcloud compute ssh evabot@evabot-agent-vm --zone=europe-west3-a --tunnel-through-iap
```

**Результат:**
```
Using OS Login user [evabot_online_gmail_com] instead of requested user [evabot]
evabot_online_gmail_com
evabot-agent-vm
SSH OK
```

Подключение прошло через IAP tunnel, OS Login смаппил Google-аккаунт в системного пользователя `evabot_online_gmail_com`, команда `whoami` подтвердила подключение.
